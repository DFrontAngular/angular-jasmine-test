Guard funcional basado en estado

En Angular los guards pueden ser funciones que usan inject() directamente. En este caso el guard no llama a ningún endpoint: consume un observable con el estado de sesión ya resuelto.

El guard devuelve un Observable<GuardResult>, que puede ser true o un UrlTree de redirección. Con take(1) nos quedamos con el valor actual de isLogged$ y evitamos suscripciones abiertas.

Testing del guard sin HTTP

Como el guard no realiza peticiones, el test no necesita HttpTestingController. Lo importante ahora es mockear la fuente de estado que consume.

En este ejemplo usamos un BehaviorSubject<boolean> para controlar el valor emitido por isLogged$. Así comprobamos de forma determinista si el guard permite o redirige.

Si el guard depende de estado ya cargado, el test debe centrarse en esa decisión y no en detalles de transporte o acceso a datos.

Ejecución en contexto de inyección

Los guards funcionales que utilizan inject() deben ejecutarse dentro de TestBed.runInInjectionContext().

El contexto de inyección es el entorno temporal que Angular crea para que inject() sepa de dónde obtener dependencias como servicios, router o tokens. Si ejecutamos la función fuera de ese contexto, Angular no puede resolver esas dependencias.

Esto garantiza que Angular pueda resolver correctamente dependencias como AuthStateService o Router.

Los tests de routing deben validar comportamiento observable en el DOM, no implementación interna del router.

Buenas prácticas aplicadas

  • ✔ Sin any en tests (strict mode)
  • ✔ Sin done() ni subscribe() manual
  • ✔ Uso de async/await + firstValueFrom
  • ✔ Tests centrados en comportamiento, no en implementación de red
El objetivo no es solo que el guard funcione, sino que sea testeable, mantenible y tipado estrictamente.
