Bloque 2 · Primer test de componente

En Angular, la mayor parte del valor está en testear componentes.

Qué estamos probando

Un componente standalone con:

  • Un Input
  • Un Output
  • Interacción del usuario
  • Renderizado en el DOM

Qué NO estamos probando

  • Métodos privados
  • Implementación interna
  • Change detection manual
Si un test necesita conocer detalles internos del componente, probablemente esté mal planteado.

Idea clave

Un test de componente en Angular es un test de integración.

Probamos el comportamiento observable desde el punto de vista del usuario.

El componente que vamos a testear

Conceptos clave del test

  • beforeEach: prepara el entorno antes de cada test para que todos empiecen desde el mismo estado.
  • imports: registra en el TestBed los componentes standalone o dependencias que el test necesita.
  • fixture: es el envoltorio de pruebas del componente; permite acceder al DOM, lanzar detección de cambios y configurar inputs.
  • component: es la instancia TypeScript del componente creada dentro del fixture.
  • detectChanges(): ejecuta la detección de cambios para que Angular procese inputs, bindings y actualice el DOM antes de hacer asserts.
  • afterEach: sirve para limpiar o verificar cosas al terminar cada test, por ejemplo spies, timers o peticiones pendientes.
  • spyOn: crea un espía sobre un método o función para comprobar si se llamó y con qué argumentos.

También se pueden anidar describe para organizar la suite en grupos, por ejemplo separando tests de renderizado, eventos o validaciones del mismo componente.

La idea es sencilla: beforeEach prepara, el fixture nos deja interactuar, detectChanges() actualiza la vista, spyOn observa y afterEach ayuda a cerrar el test de forma segura.
